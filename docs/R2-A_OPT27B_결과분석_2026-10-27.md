# R2-A GPU 비용·Latency 병목 분석 연구 기록 — OPT-2.7B FP16

- 기록일: 2026-10-27
- 연구 단계: R2-A1 Smoke 완료, R2-A2 Minimal 완료, R2-A3 Trace 완료, R2-A4 Microbench 완료; R2-A5 병목의 세부 인과 분리 여부 검토
- 목표: 높은 QKV Projection Row Skip에도 RAW SemCache 실행 경로가 Native Full Recompute보다 느린 이유를 분리하여 설명한다.
- 주의: ORACLE_DIAGNOSTIC, `safe_reuse_claimed=false`; R2-A의 FP16 재사용 모드는 Strict Correctness FAIL이므로 성능 이득이 관측되더라도 정확성 충족 성능이라 부를 수 없다.

## 3. Trace: GPU Kernel Duration과 Kernel 호출

`torch.profiler` 활성 구간의 Kernel Duration *합계*는 End-to-End 요청 Wall Time과 다르며 GPU Stream 중첩, CPU-런치 간격을 반영하지 않는다. 아래는 각각 1회 Trace의 이벤트 합계.

| Mode | 128 Kernel Duration (ms) | 256 Kernel Duration (ms) | 128 Kernel Count | 256 Kernel Count |
|---|---:|---:|---:|---:|
| Full | 22.7802 | 36.3030 | 1,958 | 1,958 |
| No-Reuse | 34.1888 | 54.4476 | 4,854 | 4,866 |
| Oracle | 27.2724 | **34.6811** | 3,974 | 4,070 |
| Contiguous | 31.7006 | 45.4742 | 4,662 | 4,770 |

**중요한 사실**: 256에서 Oracle의 전체 Kernel Duration 합계는 Full보다 약 1.62ms 짧지만 최소 계측 Wall Time은 +47.50ms 느리다. 따라서 CPU/Host 제어·런치·동기화·메모리/캐시 준비 비용을 배제한 채 GPU Kernel Duration만으로 성능을 설명할 수 없다.

분류된 주요 Kernel Duration:

| 구성요소(ms) | 128 Full | 128 Oracle | 256 Full | 256 Oracle |
|---|---:|---:|---:|---:|
| Base/LoRA QKV 태그 합계 | 6.600 | 5.183 | 9.989 | 3.679 |
| Attention-inclusive 태그 | 3.766 | 1.499 | 7.158 | 3.658 |
| FFN Up+Down | 8.704 | 8.670 | 13.750 | 13.758 |
| Executor 추가 태그 | 0 | 8.204 | 0 | 8.170 |

`attention_inclusive` 태그 시간 감소가 Attention 계산의 *물리적 생략*을 뜻하는지는 확인되지 않았다. 원래 구현의 핵심 물리적 생략 대상은 QKV Projection이다. 태그의 하위 커널/후킹 경계까지 확인 후 주장해야 한다.

Oracle Executor 추가 태그 세부 항목(ms): 128은 `fresh_assembly` 5.306, `fresh_native_qkv` 1.854, `fresh_index_preparation` 0.808, `output_allocation` 0.236. 256은 각각 5.306, 1.816, 0.773, 0.275. 이 태그를 실제 독립 비용으로 모두 더하지 않도록 주의.

Contiguous에서 `attention_impact`가 별도로 128 약 3.695ms, 256 약 10.066ms의 Kernel Duration으로 분류되며 Oracle에서 해당 태그가 없었다. No-Reuse에서도 같은 구간의 GPU 비용이 존재한다. 이것은 원 논문 캐시 관리 기능을 통합할 때 발생하는 정책/Attention 관련 비용의 실측 단서다.

GPU Memcpy 이벤트 개수: 128 및 256에서 모두 Full 5, Oracle 101, Contiguous 143. Kernel Count는 단일 Trace에서 Full 대비 약 2배 이상 증가한다. 이 값은 각 이벤트 건수이며, request wall 시간을 그대로 의미하지는 않는다.

## 4. Component Microbench

다음 값은 실제 Fixture Shape를 이용해 단독 구성 요소를 반복 실행한 평균 시간이다. 전 요청 시간에 단순 합산하거나 전체 Layer 수를 곱해 기계적으로 E2E 시간을 산출하지 않는다.

| 항목 | 128 Host (ms) | 256 Host (ms) | 128 CUDA interval (ms) | 256 CUDA interval (ms) |
|---|---:|---:|---:|---:|
| Full Native Total Projection (역할별) | 0.4560 | 0.4580 | 0.4290 | 0.4314 |
| Fresh Subset Native Total Projection (역할별) | 0.4431 | 0.4537 | 0.4184 | 0.4286 |
| Full Base | 0.1968 | 0.2261 | 0.1783 | 0.2075 |
| Subset Base | 0.1796 | 0.1817 | 0.1573 | 0.1579 |
| Full LoRA Delta | 0.2942 | 0.2945 | 0.2706 | 0.2706 |
| Subset LoRA Delta | 0.2884 | 0.3016 | 0.2648 | 0.2778 |
| Cached Slice Conversion Copy (Q/K/V 각각) | 0.0629 | 0.0653 | 0.0424 | 0.0440 |
| Snapshot Validation | **11.6773** | **23.6886** | 11.6554 | 23.6651 |
| Warm Mapping Lookup | **11.8143** | **23.7661** | 11.7914 | 23.7425 |

- Projection 입력이 전체에서 1~2 Fresh Tokens으로 줄었어도, `native_total` 개별 실행 비용은 비슷한 크기로 유지된다. 작은 GEMM 및 LoRA 실행의 고정 비용 가능성을 시사하며, 특정 Kernel 선택이나 Tensor Core 효율의 직접 증명은 아니다.
- Snapshot Validation과 Warm Mapping Lookup 측정이 매우 유사하다. 두 측정 범위 중첩 또는 Lookup 내 검증 포함 여부를 코드를 통해 확인해야 하며, **절대로 두 값을 독립된 비용으로 더하지 않는다**.
- Microbench의 `CUDA interval`은 CUDA Event 기반 구간 길이로 GPU 계산만의 순수 실행시간이 아니다. Host-GPU Submission/Launch gap도 포함할 수 있다.
- 실제 Contiguous/Oracle의 Cache Copy Audit: 128-token **61,931,520 bytes, 96 contiguous copy calls**; 256-token **125,337,600 bytes, 96 contiguous copy calls**. 각각 전체 32 Layer × QKV 3개이며, 별도 관측한 GPU memcpy 이벤트 개수와 반드시 1:1 대응하지는 않는다.

## 5. Correctness 및 Projection Audit

| Prompt | Reused | Full Projection Rows | Native Rows | Skipped Rows | Contiguous vs Full | Oracle vs Full |
|---|---:|---:|---:|---:|---|---|
| 128 | 126/128 (98.44%) | 12,288 | 192 | 12,096 | STRICT_FAIL | STRICT_FAIL |
| 256 | 255/256 (99.61%) | 24,576 | 96 | 24,480 | STRICT_FAIL | STRICT_FAIL |

- Contiguous와 Oracle 간 Executor Parity는 EXACT PASS (선택, assembled/fresh/reused, logits)다.
- Full 반복과 No-Reuse vs Full은 Exact PASS였다.
- Full 대비 재사용의 최종 Logit 최대 절대 오차: 128 = 0.01953125, 256 = 0.017578125. Tolerance 위반: 128 = 26,395, 256 = 39,174 (각 full-logit tensor 비교). 이는 이전 R1-B3-C1의 FP16 Full/Subset GEMM Shape 수치 차이와 일관된다.
- `safe_reuse_claimed=false`. FP16 Full 대비 Strict Correctness가 아직 해결되지 않았음을 항상 병기해야 한다.

## 6. 현재 가설 상태

| 가설 | 판단 |
|---|---|
| H-A: QKV가 Full GPU 비용의 작은 일부 | **정의에 따라 달라짐/미확정.** Full GPU Kernel Duration 중 QKV 태그 27~29%로 무시할 수 없는 비중이지만, 모델 전체 및 request wall과 동일하지 않고 실행 가능한 절감폭은 더 작았다. |
| H-B: Cache 제어/Assembly 비용이 크다 | **강한 지지 단서.** No-Reuse−Full(+32/+44ms), Contiguous−Oracle(+24/+51ms), Snapshot Validation(+12/+24ms), Executor 추가 태그(~8.2ms). 하지만 항목 간 인과적 분해는 미완료. |
| H-C: Fresh Subset GEMM/작은 Kernel 비효율 | **지지 단서.** Native Total Projection의 Full→Subset 개별 비용 감소가 거의 없고, Kernel Count가 증가했다. GPU Kernel/하드웨어 기작은 아직 미확정. |
| H-D: No-Reuse Wrapper 오버헤드 | **탐색적 지지.** 두 길이에서 Full 대비 +31.76/+43.69ms. |
| H-E: Oracle QKV-only도 Full보다 느림 | **탐색적 지지.** 두 길이에서 Full 대비 +35.22/+47.50ms, 각 10/10 comparisons. |

## 7. 다음 의사결정

**즉시 권장:** R2-A를 1차 병목 분석 완료로 기록하되, R2-A5(선택적, 짧은 인과 진단)에서 Snapshot Validation과 Warm Mapping Lookup 범위의 중첩 및 컨트롤/어셈블리의 각각의 독립 추가 비용만 확인. 기존 R1 실행 경로·Safety Constraint·Tolerance·문서 및 결과는 보존한다.

1. `Oracle` 실행에서 Snapshot Validation 비용을 안전하게 진단하기 위한 *diagnostic-only* immutable verified fixture 및 검증 A/B 비교 (결과는 production safe 아님으로 표기)
2. 기존 Impact/Policy를 제거한 Contiguous 대조 경로로 Control overhead 인과 격리. 부분 최적화한 단일 함수가 아닌 조건별 차이를 같은 paired session에서 측정.
3. Component Microbench 함수 범위 점검: `warm_mapping_lookup`이 Snapshot Validation을 포함하는지 검증.
4. GPU Fused/Compiled Executor는 구조적으로 개선 가능한 비용이 클 때만 R2-D에서 검토.
5. R2-B Exact Prefix KV Reuse 대조군을 병행하여 **Prefix 전체 Forward 생략**이 실제 지연을 줄이는지 검증. 이 대조군을 임의 Subsequence의 SemCache 안전성 보장으로 오해하면 안 된다.
6. R2-C 원 SemCache/EdgeLoRA Baseline, 네트워크 및 Personal LoRA 비용과 공정 비교 정의 감사.

**연구 결론:** 현재 RAW QKV Projection-only 재사용은 GPU QKV Projection Row를 매우 많이 생략하지만, 작은 GEMM의 고정비, Executor 조립 및 Kernel 증가, Snapshot 검증/제어 비용, 전체 FFN 유지 등의 비용이 절감 효과를 상쇄한다. 256-token에서는 Oracle의 합산 Kernel Duration이 Full보다 조금 짧음에도 Request Wall은 더 길어서 Host 중심 병목 가능성이 특히 크다. 아직 정확한 병목별 인과 비용과 커널별 하드웨어 효율을 단정하지 않는다.
