## 0. 배경 및 이 단계의 정확한 질문

### B1까지 **관측된** 사실 (업로드된 JSON 결과 기반)

| 관측 지표 | OPT-125M FP32 | OPT-2.7B FP16 |
|---|---|---|
| Case | L32/P16, L32/P31, L32/P0 | L128/P64, L128/P127 |
| 실제 Forward Skip | Prefix 위치에 해당하는 Layer·QKV·FFN 재계산 생략 확인 | 32 Layer에서 각각 S=64 또는 S=1만 계산 확인 |
| Strict | 세 Case `STRICT_PASS` | 두 Case 모두 `STRICT_FAIL` |
| Prefix 경계 Full 대 독립 Source max abs | P16: 5.72e-6 / P31: 0 | P64: 0.025390625 / P127: 0.05859375 |
| Suffix 전체 Full 대 Warm max abs | P16: 7.63e-6 / P31: 5.72e-6 | P64: 0.208984375 / P127: 0.0234375 |
| 최종 위치 max abs | 매우 작음 | P64: 0.02734375 / P127: 0.0234375 |
| Full vs Warm 예비 평균 | P16: 27.48 vs 27.40ms / P31: 26.34 vs 26.89ms | P64: 74.52 vs 76.67ms / P127: 74.40 vs 75.12ms |
| 모델·Mask·Position·Prefix Cache Integrity | B1 감사 통과 | B1 감사 통과, 반복 Logits Exact |

FP16에서 **Source Prefix 계산 자체가 Full의 Prefix 경계와 이미 다르다**는 것은 관측 사실이다. 그 원인이 FP16 GEMM Shape/Kernel 선택인지, Attention Shape/Mask·캐시 경로인지, 다른 수치 단계인지 아직 모른다. 동일한 Prefix라는 사실은 *수학적 재사용 적법성*을 뒷받침하지만, FP16 bitwise/Strict equality를 보장하지 않는다.

**연구 질문 A:** Full(X), 독립 Source(X[:P]), Warm(X[P:], past KV) 사이에서 최초 숫자 차이는 어느 Layer의 어떤 Tensor/연산에서 관측되는가? Prefix의 수치 차이와 Suffix 재계산의 수치 차이를 분리할 수 있는가?

**연구 질문 B:** Warm 지연 약 75ms 중 CPU 준비·Namespace/Cache Materialization·GPU 복제·Suffix Forward·LM Head 및 Output Cache 구축은 각각 얼마나 기여하는가? **Cache를 사전에 준비한 이상적 진단 대조군**에서도 Full을 이기지 못하는가?

## 1. 공통 계약과 실험 Scope

- 주 모델 `facebook/opt-2.7b`, `torch.float16`, OPT native `attn_implementation='eager'`, RTX 3090, batch=1, `user_a` synthetic PEFT LoRA rank8/alpha8/dropout0, `eval`, `inference_mode`, offline Hugging Face.
- 기본 케이스 **(L=128, P=64, S=64)** 와 **(L=128, P=127, S=1)**. OPT-125M FP32 (32/16, 32/31, optional 32/0)는 기능 Smoke/수치 정상 대조군.
- Full, Source, Warm 모두 `use_cache=True`, `output_attentions=True`를 포함하여 **B1과 동일한 Forward 옵션**을 기본 고정. Suffix logits vs Full `[:,P:L,:]`, Source 마지막 logit vs Full `[:,P-1,:]`은 별도.
- Prefix는 Source 독립 Forward로 생성한다. B1 일반 Warm 경로에서 Full Target K/V를 잘라 만든 캐시 사용 금지. Source K/V는 immutable snapshot 및 **요청마다 독립 Cache container** 원칙 유지.
- 원본 cache/weights/adapter/prefix IDs/mask/positions가 동일한지 검사. Mutation 혹은 API 불확실성이 발생하면 `FAILED`/`UNVERIFIED` 처리.
- 최소 요청 측정은 Source Prefill/Source Snapshot 만들기와 비싼 Hash/Hook을 제외하지만 **정상 Warm에서 필요한 매 요청 복제·준비 비용을 반드시 포함**한다. 모든 비용 정의를 `manifest.json`에 기록.
- 결과는 B1 결과를 덮어쓰지 않고 `results/r2/b15/<run_tag>/`에 별도로 남긴다.

## 2. B1.5-A: Numeric First-Divergence Audit

### A1. 세 Forward와 두 종류의 비교를 분리

`F=FULL_USE_CACHE(X)`, `S=PREFIX_SOURCE_PREFILL(X[:P])`, `H=EXACT_PREFIX_WARM(X[P:], S.KV)`.

1. **Prefix shape diagnostic:** F 각 Layer/연산의 `[0:P]` vs S 해당 Layer/연산의 `[0:P]`. Suffix 및 Cache는 아직 사용하지 않은 비교. 최초 차이를 확인.
2. **Suffix execution diagnostic:** F 각 Layer/연산의 `[P:L]` vs H 해당 Layer/연산의 `[0:S]`. 여기에는 Prefix K/V의 차이와 Suffix Shape 차이, 누적 오차가 모두 영향을 줄 수 있으므로 **곧바로 원인으로 단정 금지**.
3. **Cache diagnostic:** F와 S의 같은 Prefix 위치에 대한 실제 K/V를 Layer별 비교할 수 있다면 Head-Split/Scaling/상태까지 포함해 측정한다. Source의 K/V 길이=P, Warm 이후 L, Canonical Source=P 유지.
4. **Logits:** `full_repeat` Exact, Prefix boundary, all suffix, last-position을 B1과 동일 정의·Strict tolerance로 기록. Argmax/KL은 보조 지표.

### A2. 어느 지점을 계측할 것인가

실제 설치 버전의 OPT/PEFT 모듈명과 동작을 조사한 뒤, 다음을 가능한 범위에서 Hook/Recorder로 기록한다. **모든 Tensor를 동시에 GPU에 오래 잡고 있지 말 것**. 각 Phase/Layer 단위로 capture·비교·해제하거나 충분한 메모리 Preflight를 할 것.

| 순서 | 관측 위치 | 비교 및 가설 |
|---|---|---|
| 0 | Token Embedding + OPT Learned Position Embedding 및 Layer0 입력 | 동일 Prefix Position의 입력이 Exact한가? |
| 1 | 각 Layer의 Attention 입력 / LN 전후 | 최초 입력/정규화 오차 위치 |
| 2 | Q/K/V Base 출력 + PEFT LoRA 적용 최종 Projection 출력(가능하면 양쪽 구분) | Full L-Shape vs Source P-Shape GEMM 오차 확인 |
| 3 | Attention score/softmax/context/output projection(지원 가능 지점만) | Mask/Head/Attention 연산 수치 영향 확인 |
| 4 | Residual, FFN `fc1`, activation, `fc2`, Layer 출력 | 오차 증폭 구간 확인 |
| 5 | Final LN, LM Head, Suffix logits | FP16 출력 차이와 최초 발생점 연결 |

모든 Prefix/Suffix 비교는 토큰축 위치를 맞추고 **같은 Module·동일된 어댑터**를 사용한다. Shape, dtype, stride, backend, absolute token indices, max/mean abs, relative L2, exact_equal, strict_pass, violation counts를 기록. `first_nonzero`와 `first_tolerance_failure`는 구분. 이때 `first nonzero`가 bitwise rounding 차이일 수 있으므로 **첫 tolerance violation과 영향 증폭을 별도 정의**한다.

선택적 경로: Layer 0/1/2/4/8/16/31을 먼저 탐색하고, 최초 차이가 나타난 전후를 좁힌다. 타임라인은 이 장치의 **실제 Forward 진행 순서**를 기준으로 판단한다; 단순 Layer 번호만으로 연산 발생 순서를 확정하지 않는다.

### A3. 원인 진단의 최소 대조군

- FP32 OPT-125M에서 동일 감사가 정상 작동하는지 확인.
- 같은 OPT-2.7B FP16 입력에 대해 F 반복 Exact를 재검증.
- 같은 Layer/Weight의 **동일 입력 Tensor**를 사용하여 Full-shape batch GEMM 결과의 Prefix subset과 Prefix-only shape GEMM 출력을 비교하는 단독 counterfactual(계산 오차의 Shape 민감도 분석). Baseline과 별도.
- Native QKV Base와 LoRA Delta를 **독립 계측 가능할 때만** 구분한다. Layer0 차이가 발견돼도 이것만으로 cuBLAS 알고리즘을 특정했다고 주장 금지.
- 선택: FP16과 FP32/일부 모듈 float32 연산 비교 또는 Full-reference prefix-KV leakage counterfactual은 **통제 진단용**에서만 허용, 별도 플래그와 파일/`NON_SERVING_DIAGNOSTIC` 라벨. 특히 Full 결과에서 Prefix KV를 잘라 넣는 것은 일반 Prefix Reuse의 성능/안전성/정확성 근거로 취급 금지. 기본 B1.5 범위 밖이므로 불필요하면 구현하지 않는다.

**A 완료기준:** 정확한 최초 차이 경계가 특정되었거나, 특정하지 못한 위치/이유를 `UNRESOLVED`로 남기고 Layer-level strong evidence를 확보. Strict FAIL이면 그대로 보존한다. 구조/Mask 오류가 확인되면 B1 구현상 문제를 별도 차단 보고하되 원본 코드를 묵시적으로 수정하지 않는다.

## 3. B1.5-B: Warm Latency Boundary and Overhead Isolation

### B1. 정확히 구별할 실행 조건

| Mode | 의미 | Target Request timing | 설명 |
|---|---|---|---|
| `FULL_USE_CACHE` | B1 Full Native 전체 L Forward | **포함** | B1과 동일 `use_cache=True`, flags 고정 |
| `WARM_NORMAL` | B1 기존 일반 Warm: Prefix Cache가 이미 존재, Target마다 namespace/clone/container/forward | **포함** | 기본 비교군, B1 semantics 유지 |
| `WARM_PREPARED_DIAGNOSTIC` | Cache container/clone을 요청 시작 전에 유효하게 준비하고 Suffix만 Forward | **준비는 제외**, Forward 및 정당한 후속 작업 포함 | 이상적 분해 대조군, **실서비스 Warm과 별도 라벨** |
| `PREPARE_ONLY` | 사본 생성, Cache API 변환/container materialization만 개별 측정 | 개별 microbench | Forward 미실행, Hook/Hash 밖, 결과를 E2E에 무조건 합산 금지 |

`WARM_PREPARED_DIAGNOSTIC`은 **새로운 Cache 객체/사본을 매 반복마다 충분히 독립적으로** 준비한다. Forward 후 해당 prepared input은 소비/변형될 수 있으므로 두 번째 요청에서 재사용 금지. Canonical Source는 불변. 이 모드에서 단순 비용 제외를 통한 빠른 숫자는 **`IDEAL_DIAGNOSTIC`**으로 표시. `WARM_PREPARED`의 결과를 Full과 비교하더라도 서비스 속도 향상 주장으로 사용하지 않는다.

`WARM_NORMAL`에는 B1과 동일한 Namespace check, 입력/마스크/Position 준비, 실제 Per-request Clone/Memory Copy/Cache container, Native Suffix Forward, Output Cache 생성, Cleanup을 전부 포함. 측정 endpoint는 *pretokenized prompt → logits on GPU*, 생성 TTFT 아님. Full도 동일 return/cache/output flags.

### B2. 최소 지연 측정과 비용 프로파일을 **분리**

**Minimal paired timing (`phase=timing`)**

- `torch.profiler` OFF, module Hook OFF, 결과 Hash·CPU 전송 타이머 밖, CUDA 앞뒤 동기화.
- FP32 Smoke warmup>=3, measured>=3; FP16 diagnostics warmup>=3, measured 10 (1회 독립 Run의 탐색 값).
- Full, Normal, Prepared를 순서 균형 방식으로 같은 CASE에서 측정. 각 모드의 Fixed source, model, adapter, mask, output flags와 GPU 캐시 residency 확인.
- **Warm Target per-request Clone 비용을 반드시 포함**한 `FULL_USE_CACHE` vs `WARM_NORMAL`이 기본 `D(F,H) = Full − Normal` 비교.
- `Normal−Prepared`는 차이의 원인 후보를 좁히는 대조군이지만, 사전 준비 상태/캐시 히트/호스트 스케줄 변화까지 함께 바뀔 수 있어 복제 연산 단독 비용으로 단정하면 안 된다.
- Source cost와 최초 snapshot build는 별도 기록. `p50, p95, mean, raw samples, per-pair difference, wins`, 소수 표본 CI는 탐색적으로만.

**Instrumented phase (`phase=breakdown`)**

- 범위: Input/Mask Position Prep → Namespace Lookup/Guard → Clone/Materialize → Native Suffix Forward → Output Cache Return/cleanup. 서로 감싸는 부모 범위와 자식 범위를 표기하고 Host/Device overlap을 차단하는 사전 정의된 타이밍 범위로 분리.
- 추가 동기화가 필요한 세부 Timing은 **독립 instrumented pass**에서만 수행. Instrumented wall, CPU Host self time, CUDA Events/GPU activity를 합산하여 Minimal E2E로 표시하지 않음.
- KV 사본의 bytes, copy call, allocator bytes, kernel launches/memcpy (가능 시 torch.profiler 별도 trace), GPU memory peak; un-attributed residual은 별도로 기록.
- 실제 FP16의 75ms가 Cache Preparation인지 GPU Suffix Forward 자체인지 **근거에 따라 지지/반박/미해결** 분류. GPU 클럭/경합 모니터링 실패는 `MONITORING_UNAVAILABLE`로 기록하고 실행 실패로 위장하지 않는다.

### B3. 가설

- `B-H1`: Normal Warm의 매 요청 Clone/Cache Preparation이 요청시간 상당 부분을 차지한다.
- `B-H2`: Cache를 이상적으로 사전 준비하더라도 Native Suffix Forward + output head/attention/backend 고정비가 크다.
- `B-H3`: Full L vs Warm S의 Shape 차이에 따른 GPU Kernel/호출·동기화 구조가 FLOPs 절감을 Latency 개선으로 옮기지 못한다.
- `B-H4`: `output_attentions=True` 또는 출력 Cache API 변환 등 **동일하게 켜 둔** 모드·런타임 경로의 비용이 커서 단순 복제 비용만으로 설명되지 않을 수 있다. Optional flag OFF 테스트는 **새 구획 실험**, 양쪽 모드 동시 변경 + 정확성 재확인 + 별도 라벨 필수.

## 4. 성능·정확성 주장 분리

- Functional: F와 H에서 Position·Mask·Prefix Identity·Cache P→L 및 Decoder Layer Token Axis가 검증되면 `PHYSICAL_PREFIX_SKIP_VERIFIED`.
- Numeric: FP16 `STRICT_FAIL`을 변경하지 않고, B1.5-A의 최초 불일치 시점만 추가로 진단.
- Performance: B1.5-B의 예비 수치가 개선돼도 `correctness_qualified_speedup=false`(Strict Fail 존재 시). 단일 실행 n=10 결과를 B2 재현성 결론으로 승격 금지.
- R1/R2-A Base Forward의 `use_cache=False` 결과와 B1/B1.5의 `use_cache=True` 결과를 공식 배율로 직접 비교 금지.
- `P=127`은 99.22% Prefix Token 비율이지 FLOPs/Kernel/Latency 절감 비율이 아니다.
- FP16의 Strict 임계값은 B1과 동일; Argmax agreement와 KL은 보조 보고.

| B15-4 | 기존 결과·B1.5 취합 | Audit and Freeze | Strict status 유지, B2를 위한 최소 비용 항목과 분명한 결론 |

B15-2에서 Mask/Position/Adapter/KV Identity 구조 오류가 드러나면 B15-3의 speedup 주장/통계 결론을 차단하고 원인 기록. FP16 Strict FAIL만으로 진단 진행을 막지 않는다. GPU OOM 우려 시 선택 실험은 줄이고 128-token 우선; `--help`가 실제 구현된 옵션과 일치해야 한다.

## 7. R2-B1.5 성공 및 다음 단계

- A: Prefix 숫자 오차의 최초 출처에 대해 정확한 module/layer/kernel shape 증거 또는 제한된 `UNRESOLVED` 기록.
- B: **정상 Warm**의 요청 내 clone/prepare와 **Suffix Forward**를 분리한 실제 측정 근거; Minimal vs Instrumented를 혼합하지 않은 보고.
- Regressions: B1 및 R1/R2-A 코드/결과 불변, FP16 strict failure 무단 완화 금지.
- Deliverable: B2에 사용할 **정확성 제한**, **공정한 Full/H endpoint**, **Source 비용·cache clone 비용·cache residency**, **독립 반복을 위한 실행 조건** 확정.

이 단계가 성공해도 원래 SemCache의 임의 Semantic Subsequence/교차 사용자 KV 공유가 안전해졌다는 뜻은 아니다. B2 속도 측정의 출발 조건을 통제하는 독립 Exact Prefix 대조군이다.
