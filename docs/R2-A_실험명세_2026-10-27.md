# R2-A 실험 명세서 v1.0 — RAW SemCache GPU 연산 원가·Latency 병목 인과 분해

- 작성일: 2026-10-27 (KST)
- 프로젝트: `GP_semcache`, 기존 R1-B3 결과는 **읽기 전용 Freeze 기준선**
- 연구 단계: R2-A / R2의 첫 번째 실행 실험
- 수행 환경: SERAPH RTX 3090(24 GiB), `facebook/opt-125m` FP32 Smoke → `facebook/opt-2.7b` FP16 본 실험
- 분류: `ORACLE_DIAGNOSTIC`; `safe_reuse_claimed=false`
- 기존 표준: `w=3`, 같은 semantic cluster 내 exact token IDs + 보수적 provenance; R2-A는 새 semantic 안전성 증명이 아님
- CacheGen 압축·양자화·codec, 실제 Edge–User Device 통신, Prefix KV Forward Skip은 **본 단계 범위 밖**

## 0. 결론을 미리 정하지 않는 연구 질문

**주요 질문:** 재사용 가능한 QKV Projection 행을 거의 모두 생략하는데도 왜 `FULL_RECOMPUTE`보다 `CONTIGUOUS_REUSE`의 *target warm prompt→logits* 시간이 더 긴가?

가설(복수 원인이 공존 가능):

- **H-A (계산 상한):** Full의 QKV Projection GPU 실행 시간이 Full 전체에서 차지하는 비율이 작아서, 행 생략만으로 회수 가능한 최대 지연시간이 작다.
- **H-B (Host/control):** Semantic/Selector/Snapshot Validation/Mapping/Python Hook와 Tensor Assembly의 Host/Launch 비용이 절감분을 초과한다.
- **H-C (GPU/Memory):** Fresh 1~2-token Projection은 작은 GEMM을 유발하며 GPU 실행 효율과 Launch 특성이 Full GEMM과 다르다. QKV Gather/Copy/Scatter 메모리 동작도 추가된다.
- **H-D (Wrapper):** 재사용을 비활성화한 상태에서도 Wrapper만으로 Full 대비 의미 있는 지연이 발생한다.
- **H-E (Oracle 상한):** 사전에 검증된 Hit과 Mapping을 비용 없이 제공해도 이 Runtime의 QKV-only 방식은 Full을 이기지 못할 수 있다.

**금지할 선결론:** `QKV rows skipped=99%` → `전체 Forward FLOPs/time 99% 감소`; 프로파일러 Trace의 CUDA time 합을 곧바로 요청 E2E latency로 보는 해석; 일부 함수 Host timing 단순 합; 단일 GPU와 논문 EdgeLoRA 기준선의 직접 동일시.

## 1. R1 기준선 및 계승해야 할 제약

R1-B3-C2(3개 독립 Run × 30개 Paired, minimal, hierarchical bootstrap 10,000):

| 조건 | FULL ms | CONTIGUOUS ms | `FULL−REUSE` ms | 95% hierarchical CI, ms | Full보다 빠른 반복 |
|---|---:|---:|---:|---|---:|
| OPT-2.7B FP16 · 128-tok MAX Warm | 76.09 | 140.66 | −64.57 | [−69.44, −62.30] | 0/90 |
| OPT-2.7B FP16 · 256-tok MAX Warm | 77.62 | 180.83 | −103.21 | [−108.23, −100.78] | 0/90 |

물리적 Projection Skip: 126/128 토큰(98.44%) 및 255/256 토큰(99.61%). 측정 당시 FP16 `atol=rtol=1e-3`에서 Full vs Reuse **STRICT_FAIL**. Legacy/Contiguous 간 Parity는 PASS. R1-B3-C1은 Full/Subset GEMM Shape 차이의 통제된 인과 기여를 확인했고, 전체 Layer Full Shape로 바꾸면 Exact 복원되지만 Projection Skip은 0이 됐다.

**비교 가능성 주의:** 위 R1 숫자는 계측을 최소화한 benchmark의 기준선으로만 사용. 새로운 Profiler 수치와 직접 뺄셈하여 overhead로 분류하지 않는다. R2-A에선 동일 Run/조건 안에 새 minimal paired 비교를 둔다.

## 2. 원칙: 무엇을 측정하는가

- 단위: `prompt → next-token logits` target latency. 실제 token generation TTFT 또는 full response latency라고 부르지 않는다.
- CPU Wall clock: 적절한 CUDA synchronization을 포함한 request-level 경과 시간.
- CUDA Events: 동일 Stream의 device-timeline interval (launch 사이 idle이 포함될 수 있음); Host Python 실행시간이나 GPU 커널 Busy Time과 동의어가 아니다.
- `torch.profiler`: CPU operator `self_cpu_time_total`, CUDA/GPU operator·kernel activity, launch 수·시간, MEMCPY, operator shape/stack (지원 시); 이벤트/커널의 부모·자식·비동기 오버랩을 감안해 **합산 범주**를 엄격히 분리한다.
- 같은 Pair에서 Model/Weight/Tokenizer/Input IDs/Adapter/Attention Backend/Device/Dtype/Source Snapshot 및 Output Shape를 기록한다.
- `torch.inference_mode()`와 기존 GPU warmup 환경을 유지하고, 분석을 위한 코드 변경이 원본 실제 계산 순서를 바꾸지 않도록 한다.

### 2.1 측정 경로 (같은 fixture, 같은 모델 상태)

| ID | 측정 경로 | 목적 | 허용/비허용 |
|---|---|---|---|
| F | `FULL_NATIVE` | 같은 prompt/adapter의 원래 Full 계산 | R1 Full의 연산 의미·attention backend 유지 |
| W | `LOOKUP_NO_REUSE` / `NO_REUSE_WRAPPER` | Cache 제어/Wrapper가 포함되나 물리적 QKV 재사용 없는 경로 | 코드의 기존 79/80 경로를 재사용. 정확히 어떤 기능이 실행되는지 표시. 동일 경로 구성 불가시 `UNSUPPORTED` |
| R | `CONTIGUOUS_WARM` | R1과 동일한 실제 재사용 경로 | 기존 B2.1/B3 Executor 그대로, 온전한 Source QKV와 Mapping/검증 포함 |
| O | `ORACLE_PRESELECTED` | 미리 검증한 Source Occurrence, Mapping을 주입하여 선택·조회 비용만 격리 | 새 **진단 전용** 우회 경로. 바뀐 작업/우회한 검증을 필드로 모두 기록. R1의 정상 SemCache 성능으로 주장 불가 |
| M | `COMPONENT_MICROBENCH` | 개별 QKV Full/Subset, gather/copy/assembly, validation/selection 항목의 반복 Kernel/Host 비용 | 전체 추론 결과/Latency로 사용 금지. F/R와 동일한 Tensor shapes 및 warm state를 유지 |

**중요:** F/W/R/O가 동일한 기능을 하지 않는다면 이를 속도 결과 옆에 명확히 표시한다. Oracle 우회 상태에서 `safe_reuse_claimed`를 true로 바꾸지 않는다. 기존 R1 Runtime 수정이 필요하다면 독립 진단 Adapter/opt-in instrumentation으로 감싼다.

### 2.2 Timing 프로토콜 3개를 분리

1. **MINIMAL_PAIRED:** `torch.profiler`/자세한 Hook 해제, 3 warmups+10 measured로 Smoke/Pilot. 동등 fixture 내 F/W/R/O 순서를 seed별로 균형 조정. 해당 Run 안에서 `F−R`, `F−W`, `R−O`, `W−F` 등을 추출한다. 부호 정의는 명시. 정확성·audit은 timed block 바깥에서 수행.
2. **PROFILE_TRACE:** 1~3개의 대표 steady-state 타깃을 CPU+CUDA 프로파일러로 따로 실행해 Kernel/Operator Attribution. `record_shapes`/`profile_memory`/`with_stack` 선택적으로 켜며 overhead가 큰 경우 분할 trace를 사용한다. Raw trace 저장, MAX 크기 제한. 이 절대시간을 MINIMAL 측정과 혼합하지 않는다.
3. **COMPONENT_MICROBENCH:** 동일 Shape와 함수로 반복 전용 관측. Native Q/K/V Projection Full/Subset Base·LoRA, copy/assemble, mapping/validation, Host Python 한계. End-to-end 결과와 합산하지 않는다.

Source Build/Prefill, QKV Capture, Source Snapshot Validation/Cold Mapping의 *별도* 비용을 기록하지만 Warm Target 결과에 더하거나 빼는 경우에는 `source-existing` vs `dedicated-source` 상각 가정 명시. GPU cache capacity, dtype, CPU/GPU cache residency 고정.

## 3. 고정 실험 그리드

| 단계 | 모델/정밀도 | 입력 길이 | Coverage/Workload | 경로 | 반복 |
|---|---|---|---|---|---|
| Smoke | OPT-125M FP32 | 32 | MAX/Warm | F/W/R/O (가능한 경로) | Warmup 1~3 / Measure 2~3; trace 1 |
| Main Pilot | OPT-2.7B FP16 | 128, 256 | MAX/Warm, 기존 Source/Target Fixture | F/W/R/O | Warmup 3 / Measure 10; 각 경로 trace 1~3 |
| Selective validation | OPT-2.7B FP16 | 128, 256 | 0% 또는 mapping MISS 대조 | 해당 가능한 경로 | 각 2~5회; 원인 분리 목적 |
| Extension Gate | OPT-2.7B FP16 | 512, 1024 | MAX/Warm | F/R/O | GPU preflight 후 소규모 Pilot만; 본 실험 필수 아님 |

Main Pilot에서 병목 1~2개가 아직 구분되지 않을 때만 3개 독립 Run × 10+ Paired repeats를 추가. 기존 R1-C2의 3×30 결과를 새로운 실험의 반복으로 복제해서 사용하지 않는다.

**견고성:** Outlier 임의 제거 금지; `mean`, `p50`, `p95`, std, paired wins, 각 run의 GPU 온도/clock/power 조회 성공 여부와 실패 원인 별도 보고. GPU 상태 조회 실패 시 측정 자체를 임의 `PASS` 처리하지 않고 누락 기록. 실행 중 큰 파일/모델 로딩은 timed region 밖.

## 4. 원가표: 프로파일러 범주 및 감사 필드

1. `embedding_and_position`, `layernorm`
2. `q_base`, `k_base`, `v_base`, `q_lora`, `k_lora`, `v_lora`
3. `attention_score_qk`, `attention_softmax`, `attention_weighted_v` (backend가 fused면 `fused_attention`으로 표시; 억지 분해 금지)
4. `attention_output_projection`
5. `ffn_up`, `ffn_activation`, `ffn_down`
6. `lm_head_and_logits`
7. `semantic_encode`, `cluster_and_w3`, `lookup_and_selection`, `source_occurrence`, `snapshot_validation`, `mapping_prepare_hit_miss`
8. `cache_fetch`, `cache_gpu_copy`, `qkv_assemble_contiguous`, `qkv_scatter`, `hook_interception`
9. `kernel_launch_and_cuda_runtime`, `cuda_memcpy`, `allocator`, `unknown_or_unattributed`

**중요한 감사 규칙:**

- 기록 가능한 경우 모듈/Op 경계에 opt-in `record_function` 또는 NVTX range를 붙인다. PEFT/Base/LoRA/Attention/FFN 동작을 실제 추적한 근거 없이 이름만 보고 Kernel을 분류하지 않는다.
- 프로파일러의 `self` time과 inclusive time을 섞지 않는다. CUDA operator attribution과 raw GPU kernel duration은 중복 계상 가능하므로 별도의 표로 유지한다.
- 동일 CUDA stream에서 순차 커널의 총 Busy Time과 wall time의 차이는 scheduling/idle과 기타 Runtime 비용을 포함할 수 있다. Overlap 시 단순 합산은 부정확하다.
- 각 프로파일러 결과에 `unsupported/unattributed` 비율과 분류 정확도를 보고하며 불명확한 Kernel은 `unknown`으로 남긴다.
- 실제 Full/Subset GEMM Shape, strides, dtype, operation count, CUDA kernel count, tensor copy 바이트, peak VRAM, Projection skipped/native rows를 검증한다. `torch.profiler`만으로 occupancy/Tensor Core utilization 또는 특정 cuBLAS 알고리즘을 확정하지 않는다; Nsight 필요성을 분리 기재.
- `CUDA_LAUNCH_BLOCKING=1`은 Main Benchmark 환경에 사용하지 않는다. 오류 진단 모드가 필요하면 별도 Run으로 표시한다.

## 5. 인과 진단용 차이분석 (동일 Paired 최소 계측)

정의: `D(X,Y)=T_X - T_Y` (양수면 X가 더 느림).

- `D(R,F)` = 우리가 설명하려는 Warm Full 대비 Reuse 추가 지연.
- `D(W,F)` = 기존 No-reuse Wrapper/Control Overhead의 *관측치*. 경로가 정확히 일치하는지 먼저 Audit.
- `D(R,O)` = 사전선택 Oracle로 제거한 항목의 *통제된 추정*. O가 Snapshot/Semantic 기능도 제거했다면 범위 이름과 누락된 안전성 비용을 분명히 기록.
- `D(O,F)` = 이상적 매핑 비용을 제거해도 남는 실행 격차. **상한 진단 결과로만** 사용.
- `QKV_cost_full` = F의 실제 Native QKV Base+LoRA CUDA operator/kernel time (서로 독립적인 분류만 합산). 이 값은 QKV Projection-only 절약 가능한 GPU 비용의 후보 상한이지, End-to-end speedup 보장이 아니다.
- 비중: `QKV_cuda_kernel_ms / FULL_gpu_kernel_busy_ms`와 `QKV_cuda_kernel_ms / FULL_wall_ms`를 분리. Fragmentation/overlap 및 unknown kernel 존재 시 상한/하한과 미분류량을 표시.

**필수 검증:** `D(R,F)`를 독립 항목의 단순 덧셈으로 100% 강제 설명하지 않는다. 명확한 분리 가능한 제어 항목은 차이실험으로 검증하고, 남는 차이는 `unattributed_residual`로 보존한다.

## 6. Correctness / Safety / 재현성 요구조건

- F vs F 반복, 기존 Legacy vs Contiguous parity, Snapshot backing, same Input/Adapter/Layer/Position/Mapping identity audit, R/O의 실제 QKV skipped rows/unique reuse coverage 확인.
- R/O FP16 vs F strict `atol=rtol=1e−3` FAIL 예상: **그대로 `STRICT_FAIL`로 기록**. Argmax 등으로 덮지 않는다. R2-A 프로파일링 자체가 유효하다는 점과 correctness-qualified performance 주장은 분리한다.
- `--instrumentation`에 따른 결과 비교를 동일한 속도 측정으로 혼용하지 않는다.
- `model.eval()`과 `torch.inference_mode()` 사용, 같은 attention backend/output_attentions use/cache settings, token length/batch size, next-token logits 구간을 검증.
- 기존 `scripts/69`~`82`, 기존 tests, config, R1 results/Slurm script/CacheGen files 절대 임의 수정 금지.
- Git branch/HEAD/dirty status, 변경 파일 SHA256, model/tokenizer commit, adapter hash, Torch/PEFT/Transformers/Python/CUDA/GPU driver, device UUID, seed/order seed, cache residency, GPU preflight 포함.
- 24GiB RTX 3090 메모리에 대해 활성 trace 개수·retained tensors 제한. OOM/unsupported profiler는 분류 가능한 `FAILED/UNVERIFIED`를 남기고 이전 결과 손상 금지.

## 8. 종료 Gate (원인 분석에 충분한 증거)

- [ ] OPT-125M FP32 GPU Smoke에서 F/W/R/O 경로와 profiler trace가 실제 실행된다.
- [ ] OPT-2.7B FP16에서 기존 128/256-token R1 Fixture, MAX/Warm, 실제 skip 행수 및 Strict FAIL 재현.
- [ ] 동일한 R2-A Run의 **Minimal Paired**로 F/W/R/O 비교. R1-C2와 같은 결과 방향인지 교차 확인.
- [ ] Full의 QKV/Attention/FFN/LM head GPU 비용과 R의 추가 Host/Launch/Copy 비용의 대략적인 원가표; 미분류 범주를 공개.
- [ ] 적어도 H-A~H-E 가설마다 `supported / contradicted / unresolved` 및 실험 증거 제시.
- [ ] Profile Trace 결과와 Minimal Latency의 절대값 합산 금지 준수.
- [ ] Oracle 비용제거 대조군으로 R2-D(같은 Executor 개선) vs R2-B(Forward Prefix reuse) 중 우선순위를 정할 수 있다.
- [ ] R1 Freeze와 충돌하지 않으며 후속 R2-B/C와 인터페이스가 정리됐다.
