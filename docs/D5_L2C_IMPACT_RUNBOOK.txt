1. Paper abstraction versus actual path

The user-supplied paper assumption and repository Eqs15-20 specification
(docs/paper_experiment_spec.md:74) distinguish effective FLOP/s from time:

  T_QKV_ES ~ 6*N*d*d/fES; T_LoRA_UD ~ 6*N*d*r/fUD.
  T_QKV_ES / T_LoRA_UD ~ (d/r)*(fUD/fES).

Under that analytical counting d=2560/r=8 gives d/r=320. Actual D5 cpu_deltas
performs BOTH A and B linears for Q/K/V (six CPU linears); with multiply-add=2
FLOPs this is about12*N*d*r versus6*N*d*d for ES QKV, giving d/(2*r)=160.
Do not silently equate the repository paper-model6*N*d*r proxy with this exact
implementation's physical operation count. Neither counting convention makes
fES>>fUD alone establish negligible ES latency; effective rates, matrix sizes
and precision matter. Attention/FFN and
decode still execute on ES. The analytical max(ES,UD+communication)+rest_ES
expression assumes useful overlap. D5 SparseSession.correction waits for UD
response BEFORE native Linear, so that ideal overlap is not this implementation.
Current hidden wire is FP16 and QKV deltas are FP32; use actual measured bytes,
not a uniform-element paper payload shortcut or the planning wire bound.

The supplied PDF is present locally; pdftotext/native Python packages are absent.
No package was installed and no new quotation or paper result is asserted.

Observed-time categories:
 - ES Linear host scopes are native_dense_linear/native_sparse_linear; they are
   asynchronous wall/enqueue scopes, NOT isolated ES GPU kernel time. Native
   model forward includes communication and (cache modes) Impact; it is not pure
   ES compute. Pure T_ES is NOT_MEASURED without attributable GPU timing.
 - UD measured_compute_ms surrounds cpu_deltas (wall including casts/checks and
   stacking), excluding serialization/hash/TCP/pacing. It is not CPU cycles.
 - TCP send/receive scopes include peer waiting and often UD work. Do not add
   receive wait to UD cost as though disjoint. Framed bytes exclude TCP/IP packet
   headers/retransmissions. Link is application-loopback, per channel/direction.
 - Impact executes in prefill hooks, nested under native model forward.
 - Owner completion executes after decode/ACK. Tensor serialization/proof is
   nested in projection and completion. CHU/history/materialization/proofs/PBR
   are not extra disjoint timers to add to Owner completion.
 - BytePacer reserves bounded chunks before sends in BOTH directions; UD emulator
   executes LoRA once and pads measured service to cost/factor. Neither controls
   ES hardware, semantic work or machine-wide CPU resources.

Only the old attachment summaries are present in WSL. L2B's actual nine-run wire/
LoRA extraction on SERAPH is user-reported and not independently re-read here.
Thus no numeric ES/UD/communication percentage is invented. Existing extraction
CSV fields remain suitable for C_UD/sum(E2E), but receive wait is overlapping and
cannot be another independent percentage. At 50Mbps communication dominance may
increase, yet the cache-specific overhead must remain in the E2E equation.

The attached observed_profile_components.csv reports EXACT per-request reduction
exclusive wall: 2Wiki3532.541ms, Qasper3568.905ms, MultiNews3568.742ms. It does not
provide a new pure GPU T_ES. Owner inclusive and serialization timers overlap.
The reported 3-5% total QKV row saving is not a 3-5% whole-model/E2E saving.
