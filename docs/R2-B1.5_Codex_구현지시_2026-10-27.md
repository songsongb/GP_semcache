## 3. B — Warm latency decomposition and prepared-cache control

Support at least these distinct comparison modes:

1. `FULL_USE_CACHE`: unchanged B1 full native L-token forward, `use_cache=True`, `output_attentions=True`.
2. `WARM_NORMAL`: call the unchanged B1 warm request path; every per-request prefix clone, DynamicCache conversion/materialization, namespace guard, input/mask/position preparation and suffix forward remains inside the measured wall interval.
3. `WARM_PREPARED_DIAGNOSTIC`: prepare a **fresh independent** materialized prefix Cache container outside the request timer, then execute the same native Suffix Forward with equivalent output cache and cleanup semantics. Label `IDEAL_DIAGNOSTIC`, NEVER normal service latency. A prepared object consumed in a request cannot be reused in a later request. Check pre-P / post-L / source-P and cache hashes and repeat parity outside timing.
4. `PREPARE_ONLY`: separately microbenchmark cache snapshot-to-usable-request-copy/container work under the exact B1 implementation; do not invoke model forward.

Both Full and Normal must share input tokens, PEFT adapter, logits request flags, cache format constraints, device, attention backend and CUDA synchronization rules. Source build and canonical snapshot costs are excluded from conditional warm target but reported separately with exact accounting. Note that Full computes L logits whereas Warm computes S logits; report this output-shape difference as part of the baseline rather than silently calling all computation equivalent.

### Timing isolation contract

**Phase `timing`**: no torch.profiler, no added module hooks, no hashing/CPU tensor copies inside request, no extra per-component `torch.cuda.synchronize`. Use a synchronized wall around each complete Full/Normal/Prepared request. Balanced paired ordering and raw samples; warmups=3, measured=10 for FP16 pilot (exploratory, 1 independent run). `D(F,H)=Full−Normal`, positive means warm is faster. Never use earlier B1 means as simultaneous paired controls.

**Phase `breakdown`**: separate instrumented pass measuring clearly defined boundaries:

- tokenize/adapter + input/mask/position preparation (if already pretokenized, record true scope)
- namespace/cache guard or lookup
- K/V clone or tensor copy and Cache container creation
- native suffix forward (including attention, FFN, LM Head and output KV)
- return/cleanup
- optional `torch.profiler` kernel/memcpy attribution with bounded traces

Report parent/child overlap. CPU self time, CUDA event durations and GPU kernel sums/unions are **not simply additive** to request wall. Instrumented synchronizations alter schedule: never present instrumented times as minimal latency. Include GPU cache bytes, allocated/peak VRAM and number of clone/cache objects. Unknown costs should remain unknown. `PREPARE_ONLY` is a separate microbenchmark, not necessarily the marginal reduction when preparation is removed from the whole request.

A distinct option to test `output_attentions=False` is permitted only if **both** Full and Normal are simultaneously changed, strict correctness is rerun, and results are stored in a separately labeled experiment. It must not overwrite or be pooled with B1 baseline results. It is optional; first diagnose existing flags.
